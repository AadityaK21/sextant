# Entity resolution: methodology and results

Reproduce everything on this page with:

```bash
python3 eval/make_corpus.py          # only if you want to rebuild the corpus
./build/src/cli/sextant ingest --source wpi
./build/src/cli/sextant ingest --source unlocode
./build/src/cli/sextant ingest --source digitraffic
./build/src/cli/sextant ingest --source digitraffic_ais
./build/src/cli/sextant block
```

---

## 1. What is being measured, and against what

**Read this section before any number below it.**

The corpus is generated by [`eval/make_corpus.py`](../eval/make_corpus.py) and
committed, so that a reviewer who clones the repository can reproduce these
figures without downloading anything. Each record carries a hidden truth id -
the UN/LOCODE of the port, or the IMO of the hull - and the golden set is
derived from those ids.

That is ground truth **by construction**, and it is worth being precise about
what it does and does not establish.

**It does establish** that the resolver recovers identity from noisy,
disagreeing attributes. The resolver never sees the truth id. It works from
names in different cases, coordinates rounded to whole minutes, missing codes,
truncated broadcasts and reassigned MMSIs. This is the same arrangement as the
standard record-linkage benchmarks - Amazon-Google, DBLP-Scholar - where the
correspondence is curated and the matcher has to rediscover it.

**It does not establish** that the noise model matches reality. The distortions
were taken from what the real sources actually do, but a model is always kinder
than the world. The honest phrasing is *"pair completeness on a labeled set of
N pairs over the committed corpus"*, never *"on real-world data"*. Running
`data/fetch.sh` and labeling a sample of the full download would give a number
worth more; this is the number anyone can check.

**The discipline that keeps it from being circular:** the noise model was
written before the blocking keys and has never been adjusted to suit them. When
a measurement came out badly, the fix went into the resolver or into the
report, never into the generator.

### The corpus

| Source | Connector | Records | What it contributes |
|---|---|---|---|
| `wpi` | CSV | 155 | ALL CAPS names, ~25% with no UN/LOCODE, sub-locations as separate rows |
| `unlocode` | CSV | 144 | diacritics, whole-minute coordinates, non-seaport rows to filter |
| `digitraffic` | REST/JSON | 72 ports, 40 vessels | its own casing; registry vessel records |
| `digitraffic_ais` | REST/JSON | 40 vessels | truncated broadcast names, missing IMOs, reassigned MMSIs |

371 port records, 80 vessel records, 451 in total.

| Golden set | Pairs | Matches | Non-matches |
|---|---|---|---|
| `eval/golden_ports.csv` | 1,370 | 319 | 1,051 |
| `eval/golden_vessels.csv` | 272 | 37 | 235 |

The negatives are not random. Random non-matching pairs are trivially separable
and would inflate any precision figure to meaninglessness, so they are drawn
from records a blocking key would plausibly put together - same country, or a
shared name prefix - plus three forced hard cases described in §4.

## 2. Blocking results

```
451 records indexed, 4,507 keys written
2,103 blocks, largest 6, 0 purged over 200
470 candidate pairs out of 71,823 possible

reduction ratio     0.99346
pair completeness   0.9969   ports    (318 of 319)
                    1.0000   vessels  (37 of 37)
```

### Reading these two numbers honestly

**Reduction ratio** is `1 - candidates/possible`. It is trivially maximised by
blocking on nothing, so it means nothing on its own - and it is also a function
of corpus **size** as much as of the scheme. The denominator grows
quadratically while the candidate set grows roughly linearly, so the same five
keys over the full 110,000-row UN/LOCODE download would report a far higher
figure without being any better. RR is useful for comparing two schemes on one
corpus and misleading as an absolute number across corpora.

**Pair completeness** is the one that constrains everything downstream. It is a
**ceiling on the recall of the entire resolver**: a true pair blocking never
proposes is never scored, never clustered and never merged, no matter how well
the weights are tuned. At 0.9969, at most 0.3% of true duplicates are already
unreachable before the scorer sees a single feature.

The plan's target was RR > 0.999 and PC > 0.98. PC clears it comfortably. RR
does not, and the reason is the corpus size above rather than the scheme; the
comparison worth making is between blocking variants on this same corpus, which
is what §3 does.

## 3. Which key earned which recall

| Key | Candidates | True pairs | Uniquely caught |
|---|---|---|---|
| `name_prefix` | 371 | 315 | **7** |
| `name_soundex` | 358 | 290 | 0 |
| `country_name` | 288 | 288 | 0 |
| `locode_exact` | 236 | 236 | 0 |
| `geo_cell` | 231 | 167 | **3** |
| `mmsi_exact` | 34 | 31 (vessels) | 0 |
| `imo_exact` | 30 | 30 (vessels) | 0 |
| `callsign_exact` | 26 | 26 (vessels) | 0 |

The last column is the one that matters. A key that never *uniquely* catches a
true pair is paying for itself in candidate comparisons and returning nothing
another key was not already going to find.

### The finding: the phonetic key is not paying for itself

`name_soundex` produces 358 candidate pairs - the second-largest contribution -
and catches **zero** true pairs that no other key caught. On this corpus it is
pure cost.

This was predicted in the header of [`src/resolve/phonetic.h`](../src/resolve/phonetic.h)
and it is now measured. The cause is visible in the corpus: the cross-source
name variation here is casing, diacritics and truncation, and the normalizer
already handles all three before the phonetic key runs. Soundex earns its keep
when two sources *spell* a name differently - "Gothenburg" against "Göteborg" -
and this corpus does not contain that case, because the real sources it models
both derive from the same romanisation.

Two honest conclusions, and they point in opposite directions:

- **On this corpus, drop it.** That is cut number five in the execution plan,
  and the measurement supports it.
- **On the real download, measure again before dropping it.** UN/LOCODE at full
  scale contains exactly the transliteration variance this corpus lacks. Cutting
  a key because a 451-record sample did not need it would be over-fitting to the
  sample.

It stays in for now, with this table as the reason to revisit it. That is the
useful shape of the finding: not "Soundex is bad" but "Soundex is unmeasured on
the data that would justify it, and measured as useless on the data I have".

### The keys that do earn their place

`name_prefix` is the workhorse - 7 unique catches, all of them sub-location
pairs like Rotterdam against Rotterdam Botlek, where the code is missing and
the names share only a stem.

`geo_cell` earns 3 unique catches and is the only key that can work when the
names disagree **entirely**. It is also the only one that would survive a source
recording a port under a local name while another uses an English one.

`locode_exact` catches 236 pairs and none uniquely, which is not an argument
against it: it is nearly free, and it is the key that will still work when the
name normalizer meets a naming convention nobody anticipated. Cheap insurance
against a failure the other keys share.

## 4. The one pair blocking misses

```
digitraffic:NLRTM  <->  wpi:10002
```

`wpi:10002` is **Europoort**, a World Port Index row for part of the Rotterdam
port complex. It has no UN/LOCODE, its name shares no prefix with "Rotterdam",
its Soundex is different, and its coordinates are far enough from the city
centre to land outside the geohash cell and its neighbours.

Every key fails, and they fail for the same underlying reason: *nothing in that
record says Rotterdam*. A human knows Europoort is part of Rotterdam because of
domain knowledge, not because of a string or a coordinate.

The fix is not another string key. It is the `alt_names` property - the World
Port Index lists "Rotterdam Botlek" as an alternate name on the Rotterdam row -
which would connect the two through a name neither record carries in its primary
field. That is a real improvement and it is not implemented; it is written down
here rather than quietly omitted.

## 5. The hard cases the corpus contains deliberately

**MMSI transcription slips** (6 pairs). Same hull, one digit different in the
MMSI, because the transmitter was configured wrong. `mmsi_exact` cannot catch
these, and the test
`BlockingTest.CatchesPairsWhoseStrongestWeakIdentifierDisagrees` asserts that
they are found *and* that it was not the MMSI key that found them.

**MMSI reassignment** (3 pairs). An MMSI belongs to the radio licence, not the
hull, and is reissued when a vessel reflags. These three pairs have **identical
MMSIs and different IMO numbers** - the most identifying-looking field agrees
exactly and the answer is still no.

These are the pairs the whole veto mechanism exists for, and they are forced
into the golden set explicitly rather than left to random sampling. A test that
covers its most important case only by luck is a test that will eventually stop
covering it.

## 6. Scoring: precision, recall and F1

```
./build/src/cli/sextant eval
```

The weights in [`schema/resolver.yaml`](../schema/resolver.yaml) were fitted by
coordinate ascent on the **training split only**. Every number below is measured
on the held-out 20% that the tuner never saw.

| | Pairs | TP | FP | FN | Precision | Recall | **F1** |
|---|---|---|---|---|---|---|---|
| **Ports, held-out** | 266 | 56 | 1 | 0 | 0.9825 | 1.0000 | **0.9912** |
| Ports, training | 1,104 | 262 | 2 | 1 | 0.9924 | 0.9962 | 0.9943 |
| **Vessels, held-out** | 55 | 10 | 0 | 0 | 1.0000 | 1.0000 | **1.0000** |
| Vessels, training | 217 | 27 | 0 | 0 | 1.0000 | 1.0000 | 1.0000 |

Tuning moved ports from 0.9501 to 0.9943 on training in two passes, and it
converged rather than hitting the iteration cap. The plan's target was F1 > 0.90
on the holdout.

### Only a MATCH counts as a positive

A pair in the REVIEW band counts as a **non-match** for the metric. That is the
honest accounting: a pair a human has not looked at is not a resolved pair, and
a resolver that pushes everything difficult into review should not be rewarded
for it. One true port pair sits in review under the shipped weights and is
counted as a miss.

### Why the vessel numbers are perfect, and why that is not impressive

When both records carry an IMO, one exact comparison settles it - an IMO is
assigned to the hull for life. The only interesting vessel cases are the three
MMSI reassignments, and those are handled by a veto rather than by the scorer.
So a perfect vessel F1 says the veto works, not that the scorer is clever. The
port task is the one carrying real signal, and it is the number to quote.

### What tuning actually changed

Two weights moved: `name_exact` 3.0 to 5.0, and `country_match` 1.0 to 3.0.

The reason is visible in the data rather than mysterious. The Digitraffic port
feed carries **no coordinates at all**, so a pair where neither record has a
UN/LOCODE scores on name and country alone. At the starting weights that
totalled 4.0 and landed in the review band. Raising them is safe because a
country *disagreement* is already a veto - the weight only ever fires on pairs
that agree, so it is not being asked to outvote contrary evidence.

## 7. Clustering: the comparison that justifies the design

```
./build/src/cli/sextant resolve
```

```
459 source records, 470 candidate pairs
365 match, 2 review, 101 vetoed

clustering             clusters  largest singletons  refused
transitive union-find       182        6          6        -
veto-constrained            187        5          6       10
```

Measured over the pairs each clustering **implies** - every pair of records
sharing a cluster - rather than over the edges the scorer decided:

| Clustering | Precision | Recall | F1 |
|---|---|---|---|
| Transitive union-find | 0.9726 | 1.0000 | 0.9861 |
| **Veto-constrained** | **1.0000** | **1.0000** | **1.0000** |

### Why the pairwise F1 above cannot see this

Precision and recall in §6 are computed over pairs the scorer decided
individually. Matching is not transitive, so a chain of three individually
reasonable decisions - A resembles B, B resembles C - can produce a cluster
that is wrong as an entity while every pairwise decision in it looks defensible.

Plain union-find loses 2.7 points of precision to exactly that. It is not one
wrong entity either: an over-merge welds two clusters together permanently and
every record in both is now wrong.

The constrained version processes match edges in **descending score order** and
refuses any merge that would place two vetoed records in one cluster. It refused
10 merges here and recovered all of the precision, at no cost to recall.

### The ordering matters

Highest confidence first is not cosmetic. Once two clusters are joined, every
veto spanning them blocks nothing - the damage is already done. Making the
most reliable merges while there is still room to refuse the unreliable ones is
what makes the constraint effective rather than arbitrary.

## 8. Fusion and the resolved entities

```
187 entities written, 1,303 properties, 1,303 provenance records
dedup ratio 0.5926  (459 records -> 187 entities)
```

Every property carries a provenance record naming the winner's source row, its
transform chain, the rule that chose it, and **every rejected alternative with
the reason it lost**:

```
name = "Rotterdam"
  rule       most_trusted
  origin     unlocode batch 1 row 2, column NameWoDiacritics
  chain      trim -> collapse_ws -> title_case
  rejected   "ROTTERDAM"  from wpi row 10000, column Main Port Name
             lower source trust (0.80 < 0.95)
```

That is the difference between an answer and an assertion, and it is why the
rejected values are stored rather than discarded.

### The rules, and why each property gets a different one

| Property | Rule | Why |
|---|---|---|
| `locode`, `name` | `most_trusted` | UN/LOCODE is the code authority; when it disagrees with the World Port Index it wins |
| `lat`, `lon` | `numeric_median` | resists one bad coordinate entirely - a mean would let it drag the answer halfway |
| `flag` | `most_recent` | a reflagged vessel genuinely changed flag, so the newest observation is the true one |
| `alt_names` | `union` | a list property loses information under any rule that picks one value |

`MedianResistsOneBadCoordinate` asserts this directly: the median of
{0.0, 51.92, 51.94} is 51.92, where a mean would give 34.6.

## 9. Known limitations

**Records are held in memory during resolution.** At 459 records that is a few
megabytes and it is what makes the tuner's inner loop feasible. At the full
UN/LOCODE scale it would have to stream, and the tuner would have to work from
cached feature vectors on disk. This is a real limit, not a detail.

**The distance veto never fires on this corpus.** It is checked after the
locode and country vetoes, and blocking only proposes pairs that already share
a code, a name or a geographic cell - so everything it would catch has been
rejected for a more specific reason first. It stays because the blocking scheme
is configuration, and `DistantPortsAreVetoedWhenNothingElseRejectsThemFirst`
exercises it directly so that a rule nobody runs is still a rule somebody tests.

**A weighted sum, not a learned model.** With a few hundred labels a logistic
regression would overfit, and it would destroy the per-feature explanation the
lineage panel depends on. Given 10⁵ labels the right answer changes - use the
model, keep the feature vector as the explanation layer.
